# Work Log

세션의 작업 내용과 다음 워킹데이 계획을 Obsidian 업무일지에 기록한다.
**세션 종료 시 반드시 실행**하여 다음 세션의 컨텍스트 연속성을 보장한다.

## 빠른 시작

```
/work-log           → 오늘 일지 신규 생성 또는 업데이트 (세션 종료 시)
/work-log update    → 기존 일지에 새 작업만 추가 (중간 저장)
/work-log resume    → 직전 워킹데이 일지를 읽고 컨텍스트 복원 (세션 시작 시)
```

---

## Arguments
- 인자 없음: 오늘 일지를 새로 생성하거나, 기존 일지가 있으면 새 작업만 추가
- `update`: 기존 일지에 이후 진행한 내용만 추가 (중간 저장)
- `resume`: 직전 워킹데이 일지를 읽고 요약하여 컨텍스트 복원

## Configuration
- **저장 경로**: `$OBSIDIAN_VAULT_PATH/40-DevLog/`
- **파일명**: `{YYYY-MM-DD}_daily-log.md`
- **태그**: `claude-code`, `work-log`

---

## Process

### Mode A: `resume` — 세션 시작 시 컨텍스트 복원

1. `$OBSIDIAN_VAULT_PATH/40-DevLog/`에서 최신 일지 파일을 찾는다 (오늘 제외, 가장 최근 날짜)
2. 해당 일지를 Read로 읽는다
3. 사용자에게 간결하게 요약하여 제시한다:
   - **어제 핵심 작업** (3줄 이내)
   - **논의/결정 사항** (있으면)
   - **오늘 계획** ("다음 워킹데이 계획" 섹션에서)
4. 오늘 계획 중 미완료 항목이 있으면 이어서 진행할지 확인한다

### Mode B: 기본 / `update` — 세션 종료 시 기록

#### 1. 기존 일지 확인
오늘 날짜의 일지 파일이 존재하는지 Read로 확인한다:
- 경로: `$OBSIDIAN_VAULT_PATH/40-DevLog/{YYYY-MM-DD}_daily-log.md`

#### 2. 대화 컨텍스트 분석
현재 세션에서 수행한 작업을 분석한다:
- 어떤 파일을 수정/생성했는가
- 어떤 문제를 해결했는가
- 어떤 결정을 내렸는가
- **사용자와 어떤 논의/고찰이 있었는가** (작업뿐 아니라 대화에서 나온 방향성, 비판, 인사이트)
- 미완료 작업이 있는가

#### 3-A. 신규 생성 (기존 일지 없음)
파일을 새로 생성한다:

```markdown
---
tags: [claude-code, work-log]
created: {YYYY-MM-DD}
updated: {YYYY-MM-DD}
project: {주로 작업한 프로젝트명, 여러 개면 쉼표 구분}
---

# {YYYY-MM-DD} ({요일}) — {한줄 요약}

> {Phase 또는 맥락 한 줄}

## 작업 요약
{1-2문장 전체 요약}

---

## 작업 로그

### 1. {작업 제목}
{작업 내용 상세}

#### 수정/생성 파일
{해당하는 경우 테이블 또는 리스트}

#### 개선 효과 / 해결한 이슈
{구체적인 before/after 또는 효과}

---

## 논의 & 결정
{세션 중 나눈 주요 논의, 고찰, 방향 결정을 기록한다.
작업 로그에 담기지 않는 "왜 이렇게 했는가", "어떤 부족함을 느꼈는가" 등의 맥락.
논의가 없었으면 이 섹션을 생략한다.}

## 느낀점
{기술적 인사이트, 배운 점}

## 다음 워킹데이 계획
{반드시 작성. 다음 세션에서 이어받을 작업 목록.}

- [ ] {할 일 1}
- [ ] {할 일 2}
- [ ] {할 일 3}
```

#### 3-B. 기존 일지에 추가 (기존 일지 있음)
1. 기존 일지를 Read로 읽는다
2. 이미 기록된 내용과 현재 대화 컨텍스트를 비교한다
3. **아직 기록되지 않은 새 작업만** 식별한다
4. 기존 일지의 마지막 섹션 번호를 확인하고 이어서 번호를 매긴다
5. `느낀점` 섹션 위에 새 작업 섹션을 삽입한다
6. `느낀점`에도 새로운 인사이트가 있으면 추가한다
7. **`다음 워킹데이 계획`을 현재 상태에 맞게 갱신한다** (완료 항목 체크, 새 항목 추가)
8. **`논의 & 결정` 섹션에 새 논의 내용을 추가한다** (있으면)
9. frontmatter의 `updated` 날짜를 오늘로 갱신한다
10. 필요시 `project` 필드에 새 프로젝트명을 추가한다

#### 4. 결과 보고
- 생성/수정된 파일 경로
- 추가된 작업 항목 요약 (1줄씩)
- **다음 워킹데이 계획 요약** (반드시 표시)
- 신규 생성인지 업데이트인지 명시

## 필수 섹션 체크리스트

| 섹션 | 필수 | 설명 |
|------|------|------|
| 작업 요약 | Y | 1-2문장 전체 요약 |
| 작업 로그 | Y | 번호 매긴 작업 상세 |
| 논의 & 결정 | 조건부 | 대화에서 방향성/고찰/비판이 있었으면 필수 |
| 느낀점 | Y | 기술적 인사이트, 교훈 |
| **다음 워킹데이 계획** | **Y** | **미완료 + 새 계획. 빈 상태로 두지 않는다** |

## Writing Guidelines
- 대화/설명은 한국어, 코드/변수명은 영어
- 작업 제목은 간결하게 (예: "KT 스크래퍼 버그 수정", "Playwright 다운로더 구현")
- 수정 파일은 프로젝트 루트 기준 상대 경로 사용
- 개선 효과는 구체적으로 (before/after, 수치, 영향 범위)
- 느낀점은 기술적 인사이트 중심 (감상이 아닌 교훈)
- **논의 & 결정은 "왜"에 집중** — 결론만이 아니라 그 결론에 이른 맥락을 남긴다
- **다음 계획은 구체적으로** — "Phase 2 시작" ✗ → "Tech Radar 컴포넌트 설계 + API 스펙 초안" ✓
